# TikTok モニタリング Bot

GitHub Actions を使って TikTok アカウントの新規投稿を自動検知し、Slack へ通知するボットです。投稿から 24 時間後にパフォーマンス指標（再生数・いいね数など）を再取得して報告します。

## 機能

- **新規投稿検知**: 登録アカウントを定期的にチェックし、新しい投稿を検出したら Slack へ通知
- **24 時間後アナリティクス**: 検出した動画の再生回数・いいね数・コメント数・シェア数・保存数を、**投稿時刻から** 24 時間後に収集して Slack へ報告
- **週次レポート**: 毎週月曜の午前中に稼働状況サマリーを Slack へ送信
- **状態管理**: 既知の動画 ID やアナリティクスジョブをアカウントごとのファイル (`data/accounts/`) に保存し、git にコミット
- **通知の出し分け**: アカウントごとに Slack 通知の有無を設定可能。通知を切っても収集は継続し、障害通知だけは届く

### 実行間隔について

`run.yml` の cron は 1 時間ごと (`7 * * * *`) です。GitHub Actions のスケジュール実行はベストエフォートで、**高頻度の指定ほど間引かれます**。

以前は 5 分ごと (`*/5`) を指定していましたが、1 日 288 回の要求に対して実際に届いていたのは **14〜17 回**（配信率およそ 5%、実効間隔 85〜100 分）でした。一方、週次レポート (`0 0 * * 1`) は 23 週分を調べて**欠落ゼロ**です。低頻度の指定は間引かれずに届くため、要求を 1 日 24 回に落としています。設定上は減速ですが、実際の実行回数はむしろ増える見込みです。

分を `:07` にしているのは、監視対象アカウントの**投稿の 82% が毎時 :00 ちょうど**に行われているためです（直近 60 件を計測）。毎時の早い時間に確認するほど検知の遅れが小さくなります。`:00` ちょうどを避けているのは、GitHub が毎時 0 分を高負荷時間帯として明記しているためです。

なお投稿時刻は 7 時台と 19 時台（JST）に集中しています（60 件中 42 件）。検知の速さをさらに詰めるなら、この 2 つの時間帯に実行を寄せる余地があります。

いずれにせよ遅延は残ります（週次レポートの実測で中央値 61 分）。投稿検知が多少遅れても 24 時間後アナリティクスの精度には影響しません（計測は投稿時刻を基準にしているため）。確実に短い間隔で回したい場合は、外部スケジューラから `workflow_dispatch` を叩く構成が必要です。

## 動作環境

- Python 3.12
- [yt-dlp](https://github.com/yt-dlp/yt-dlp) (TikTok データ取得)
- GitHub Actions (定期実行)
- Slack Incoming Webhook (通知)

## セットアップ

### 1. リポジトリの準備

このリポジトリをフォークまたはクローンしてください。

### 2. Slack Incoming Webhook の設定

1. Slack の **App 管理画面** → **Incoming Webhooks** でウェブフックを作成
2. 発行された Webhook URL をコピー

### 3. GitHub Secrets の登録

リポジトリの **Settings → Secrets and variables → Actions** から以下のシークレットを登録します。

| シークレット名 | 説明 |
|---|---|
| `SLACK_WEBHOOK_URL` | Slack Incoming Webhook の URL |

### 4. 監視アカウントの設定

`config/accounts.json` に監視したい TikTok アカウントを追加します。

```json
{
  "accounts": [
    { "username": "@username1" },
    { "username": "@username2", "notify": false }
  ]
}
```

> アカウント名は必ず `@` から始めてください。

`notify` を `false` にすると、そのアカウントは**データ収集だけ行い Slack へは通知しません**。新規投稿と分析結果の通知が止まります。既定は `true` です。

ただし**障害通知（3 回連続の取得失敗）と復旧通知は `notify` の設定に関わらず送られます**。収集専用のアカウントが、誰にも気付かれないまま収集を止めてしまうのを防ぐためです。

`"@username1"` のように文字列で書くこともできます。その場合は `notify: true` として扱われます。

## 実行の流れ

`run.py` が唯一のエントリーポイントです。設定されたアカウントを 1 つずつ処理し、各アカウントについて次を順に行います。

1. `data/accounts/<アカウント名>.json` を読み込む
2. **新規投稿の検知**（`monitor.check_account`）— 新しい投稿を Slack へ通知し、24 時間後のアナリティクスジョブを登録する
3. **アナリティクスの収集**（`analytics.collect_due_analytics`）— 期限が到来したジョブの指標を取得して Slack へ通知する
4. 内容に変化があればファイルを保存する

全アカウントを処理したあと、変更があったファイルをまとめて 1 回コミットして push します。

2 と 3 は同一プロセス内でひとつの状態オブジェクトを共有します。**各ファイルの書き手が常に 1 つだけ**になるため、両者が互いの変更を git push の競合で失うことがありません。以前は 2 本の独立したワークフローが同じファイルを更新しており、push に失敗した側の変更が失われて同じ動画を再通知する可能性がありました。

いずれかのアカウントやフェーズが例外で落ちても、他のアカウントの処理は続行され、すでに書き込まれた内容は保存されます。その場合ワークフローは失敗として終了するので、Actions の画面で気付けます。

## 状態管理の仕組み

データは**アカウントごとに 1 ファイル**（`data/accounts/<アカウント名>.json`）で保持し、内容に変化があったファイルだけを git へコミットします。

| キー | 用途 |
|---|---|
| `known_video_ids` | 通知済みの動画 ID。ここに無い動画を「新規投稿」と判定する |
| `pending_analytics` | 24 時間後のアナリティクス取得待ちジョブ |
| `completed_analytics` | 取得済みのアナリティクス履歴（**アカウントごとに**最新 200 件まで保持） |
| `consecutive_failures` | 連続取得失敗回数。閾値で頭打ちにする（失敗中のみ存在） |
| `failure_notified` | エラー通知済みフラグ。再送を防ぐ（失敗中のみ存在） |

アカウントごとに分けているため、投稿の多いアカウントが他アカウントの履歴を保持上限から押し出すことがなく、アカウントの追加や削除も他に影響しません。1 回の実行での差分も、実際に更新のあったアカウントのファイルに限定されます。

> **移行について:** 以前は全アカウント分を `data/state.json` にまとめていました。このファイルが残っている場合、次回の実行時に自動でアカウントごとへ分割され、元のファイルは削除されます。移行時に履歴の間引きは行いません。設定から外したアカウントのデータも失われないよう、`state.json` に含まれる全アカウントが対象になります。

### 計測タイミング

アナリティクスの取得期限は、**投稿時刻**から 24 時間後で計算します。投稿時刻は yt-dlp が返す値をそのまま使います（取得できなかった場合のみ検知時刻を基準にします）。

検知はポーリングなので、投稿から検知までにタイムラグがあります。検知時刻を基準にすると、このラグと「期限到来から次の実行まで」のラグが加算され、実測で平均 2 時間ほど 24 時間から後ろへずれます。投稿時刻を基準にすることで前半のずれが無くなります。

それでも実行間隔の分（実測で平均 1 時間程度）は遅れるため、`completed_analytics` には実際の経過時間を `elapsed_hours` として記録します。厳密に 24.0 時間後の数値ではないので、投稿間で比較する際はこの値で正規化するか、許容範囲で絞り込んでください。Slack 通知にも「投稿から N 時間後の数値です」と表示されます。

検知した時点で既に計測期限を大きく過ぎている投稿には、アナリティクスジョブを登録しません。ボット停止後の再開時などに、40 時間後の数値が 24 時間データとして混ざるのを防ぐためです。許容する遅れは `config.py` の `analytics_max_lateness_hours`（既定 6 時間）で調整できます。

失敗トラッキング用の 2 キーは、正常時には書き込まれません。復旧するとキーごと削除されるため、健全なファイルは投稿データだけを含みます。カウンターを閾値で頭打ちにすることで、障害が続いてもファイルが変化せず、無駄なコミットが発生しません。

初回実行時は、そのアカウントの既存投稿を通知せずに `known_video_ids` へ記録します。

## Slack 通知の種類

### 新規投稿検知

新しい投稿が見つかった際に送信されます。アカウント名・検出時刻・タイトル・動画リンクを含みます。

### 24 時間後アナリティクス

投稿から 24 時間経過後に再生回数・いいね数・コメント数・シェア数・保存数を報告します。

### エラー通知

以下の場合に通知します。

- 同一アカウントの投稿取得が **3 回連続で失敗**した場合（アカウントの削除・非公開化、レート制限、yt-dlp の破損など）
- アナリティクス収集が最大リトライ回数（3 回）に達した場合

取得失敗の通知は、障害が続いても**復旧するまで再送しません**。復旧を検知した時点で復旧通知を送り、カウンターをリセットします。

閾値の 3 回は約 4 時間の異常継続に相当します（実行間隔が約 1〜1.5 時間のため）。`src/config.py` の `failure_alert_threshold` で変更できます。

### 週次レポート

毎週月曜の午前中に、ボットの機能説明と現在の監視アカウント一覧を送信します。

## ローカル実行

```bash
pip install -r requirements.txt

export SLACK_WEBHOOK_URL="https://hooks.slack.com/services/..."

# 投稿検知とアナリティクス収集（本番と同じ処理）
python src/run.py

# 週次レポート
python src/weekly_report.py
```

> **注意:** `run.py` は内容に変化があると `data/` 配下をコミットして push します。ローカルで試す場合は、意図しないコミットが発生しないよう作業ブランチを切ってから実行してください。

## テスト

```bash
pip install -r requirements-dev.txt
pytest
```

TikTok・Slack・git はすべてスタブに差し替えてあります。テスト実行時にネットワークアクセスは発生せず、実際の `data/` 配下も書き換わりません。PR と main への push で CI が自動実行されます（`data/` と Markdown のみの変更では実行されません）。

既知のバグは `xfail` マーカーで追跡しています。修正されると「想定外に成功した」として CI が落ちるので、マーカーの外し忘れに気付けます。
